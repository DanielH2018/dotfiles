# Config review + soak gate

**Date:** 2026-07-08
**Status:** Proposal (branch `config-soak-gate`)
**Backlog item:** #2 — "treat `.claude/` changes like code: a lightweight review + soak step before behavior-affecting config lands"

## Problem

Behavior-affecting Claude Code config — `settings.base.json` (source of the generated
`settings.json`), hooks, agents, skills, and `CLAUDE.md` — changes the way the agent behaves,
often subtly. A one-line system-prompt tweak once cost Anthropic ~3% quality and went undetected
for weeks. In this repo the same class of change (a reworded hook message, a new deny rule, a
tweaked agent prompt) lands silently: `chezmoi apply` deploys it and nothing records *that* it
changed or *when*, so there is no window in which a regression is expected to surface before the
change is trusted.

We want two properties, cheaply and deterministically:

1. **Surfaced, not silent** — a behavior-affecting change must be consciously acknowledged before
   it counts as reviewed.
2. **Soaked** — record when each change landed; only flag it "stable" after an observation window
   has elapsed without further change.

## Chosen approach: a committed fingerprint ledger + CLI gate

A small repo-level Node CLI, `bin/config-soak`, backed by a committed JSON ledger,
`config-soak.json`.

- **`config-soak status`** scans the tracked config surface, fingerprints each file (sha256),
  and diffs against the ledger. It classifies every file as `unrecorded`, `changed`, `removed`,
  `soaking`, or `stable`, prints a report, and **exits non-zero** if any file is
  `unrecorded`/`changed`/`removed` (an unreviewed change). That non-zero exit is the gate.
- **`config-soak land [PATH...]`** records the current fingerprints as reviewed, stamping
  `landed = now` for new/changed files and **preserving** the timestamp of unchanged files (the
  soak clock is not reset by an unrelated change elsewhere). This is the deliberate "I reviewed
  this" act. With no arguments it acknowledges everything; with paths it acknowledges only what
  you actually reviewed.
- A file is **`soaking`** until `now - landed >= windowDays` (default 7), then **`stable`**.
  Editing a file bumps its fingerprint, so it re-enters `changed` and its clock restarts on the
  next `land` — a change is never silently trusted.

The logic is split so it is trivially testable:

- `bin/config-soak-lib.js` — **pure** functions (`fingerprint`, `buildReport`, `gateFailures`,
  `land`). No filesystem, network, or clock: `now` and the scanned inputs are injected. All unit
  tests exercise this module with in-memory data, so they are deterministic and never flaky.
- `bin/config-soak` — a thin CLI shell that does the impure work (walk the tree, read/write the
  ledger, read the wall clock, set the exit code) and delegates all decisions to the lib.

### Tracked surface (declared in `bin/config-soak`)

| Path | Why |
|---|---|
| `home/.chezmoitemplates/settings.base.json` | source of the generated `settings.json` |
| `home/private_dot_claude/CLAUDE.md.tmpl` | global instructions |
| `home/private_dot_claude/hooks/**` | deterministic behavior injected around tool use |
| `home/private_dot_claude/agents/**` | subagent system prompts |
| `home/private_dot_claude/skills/**` | skill instructions |

Fingerprints are taken over the **chezmoi source** files (`executable_*`, `*.tmpl`) — the
reviewable source of truth — not the rendered/deployed output. Commands are deliberately excluded
to match the backlog's stated surface (YAGNI); adding a row to the table extends coverage.

## How it fits the existing architecture

- **Merge pipeline.** `settings.json` is generated by `executable_claude-settings-merge` from
  `settings.base.json` + a work overlay. The gate tracks `settings.base.json` (the committed input
  a human edits), not the generated artifact — so it reviews the source, consistent with how the
  merge already treats base as the source of truth. It never reads a machine's private work
  overlay.
- **Deterministic complement to `review-setup`.** The `review-setup` skill is an *LLM-driven audit*
  (is this hook correct? does it shellcheck? is a permission redundant?). The soak gate is the
  *mechanical ledger* it lacks: it holds no opinion on quality, only on "has this been
  acknowledged, and how long has it been stable?" The two compose — `review-setup` can judge a
  change, `config-soak land` records that judgement and starts its clock. No LLM runs inside the
  gate.
- **Not deployed.** Like `tests/` and `docs/`, `bin/` lives outside the chezmoi source root
  (`.chezmoiroot = home`), so it is repo-maintenance tooling, not a dotfile pushed to every
  machine. That is why it does not use the `executable_` name prefix (a chezmoi-source convention)
  and is a plain `chmod +x` script.
- **No CI wired.** None exists in this repo. The gate is a manual/opt-in command; a maintainer runs
  `config-soak status` before committing config changes. Natural future homes (out of scope here):
  a step in the `review-setup` flow, the daily `healthcheck`, or a pre-commit hook.

## Alternatives rejected

1. **Git hook / CI check that blocks on any `.claude/` diff.** Rejected: there is no CI, and a
   pre-commit hook that hard-blocks is heavier than asked and easy to `--no-verify` around. It also
   only answers "did it change?", not "how long has it been stable?" — it has no soak dimension. A
   committed ledger gives us the time axis and stays advisory (exit code), which the maintainer can
   wire into whatever gate they want later.
2. **Reuse git history / `git log` as the soak record.** Rejected: commit dates answer "when did
   the file last change" but not "when was this change *reviewed and accepted for soak*", and they
   can't model "acknowledge file A but keep watching file B." The ledger separates *landed*
   (accepted) from *authored*, and survives rebases/squashes that rewrite dates. It is also a
   single reviewable file in a PR diff.
3. **Track the rendered `~/.claude/settings.json` and deployed files.** Rejected: those are
   machine-specific (work overlay, OS-gated blocks) and not in the repo, so they are neither
   deterministic nor reviewable. Fingerprinting the committed source is stable across machines.

## Interface

```
config-soak status [--json]   # report; exit 1 if any unreviewed change exists, else 0
config-soak land [PATH...]     # record current config as reviewed (start/keep soak clock)
config-soak list               # print the tracked config paths
config-soak --help
```

Ledger shape (`config-soak.json`, committed):

```json
{
  "windowDays": 7,
  "entries": [
    { "path": "home/.../executable_notify.sh", "hash": "<sha256>", "landed": "2026-07-08T20:17:05.073Z" }
  ]
}
```

## Testing

`tests/config-soak-lib.test.js` (plain `node:test`, no deps) covers the pure logic: fingerprint
determinism, all five classifications, the window boundary (`>=` is stable), window precedence
(override > manifest > default), `gateFailures` counting, and `land` semantics (stamp new/changed,
preserve unchanged clock, drop deleted, path-filtered acknowledge, input immutability). No
filesystem or clock is touched, so the suite is deterministic.

Why this shape

The repo's pattern is deliberate: risky/parsing logic lives in safe_reads.py (pure, offline unit-tested), and app.py is thin FastMCP wiring. The new tool follows it exactly. Because GET /containers/json omits Env and already carries state + a (healthy)/(unhealthy) suffix in Status, the no-secrets and read-only invariants hold for free — no per-container inspect, no new data source.

Status-string parsing spec

The one risky bit. state is authoritative for the running/exited axis; the (…) suffix carries health. Enumerate the real forms:

StatusstateClassification
Up 4 days (healthy)runninghealthy — not flagged
Up 13 hoursrunningno healthcheck — not flagged
Up 11 minutes (health: starting)runningstarting — flag (soft)
Up 2 days (unhealthy)runningunhealthy — FLAG
Exited (0) 5 hours agoexitednot running — FLAG
Restarting (1) 3 seconds agorestartingcrash-looping — FLAG
Createdcreatednever started — FLAG
Fail loud. Any status string that doesn't match a known form is classified flagged/unknown, never silently treated as healthy — a parser gap must surface a container, not hide one.

Invariants & non-goals

  • read-only No write/exec path. Reads /containers/json only — same endpoint list_containers already uses.
  • no secrets List endpoint omits Env; do not switch to per-container inspect to get richer health.
  • pattern Decisions in safe_reads.py (tested); wiring in app.py.
  • scope One tool. No log/metric aggregation here.
